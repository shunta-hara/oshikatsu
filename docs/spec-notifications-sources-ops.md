# 通知強化・収集ソース拡充・運用整備 仕様書

## 概要

本仕様書は「oshikatsu」の第2フェーズとして、ユーザー体験・情報量・安定運用の3軸を強化する。新着情報をプッシュ通知（Web Push）でリアルタイムに届けることで、ユーザーが能動的にサイトを訪れなくても推し情報を見逃さないようにする。収集ソースを公式X（RSS経由）・YouTube公開フィード・イベント/ライブ告知RSS等に拡大し、情報の多様性を高める。さらに収集失敗の自動検知と通知・Neon の容量監視を加え、個人が無料で安定運用できる基盤を整える。対象ユーザーは既存の推し活ファン（モバイル・デスクトップ両対応）。

---

## 前提・設計決定

### 通知配信手段の選定

通知の配信手段として、メール通知・LINE通知・Web Push の3案を比較した。

| 手段 | 月額0円 | 実装の単純さ | 個人利用規模 | 備考 |
|---|---|---|---|---|
| メール通知（SendGrid等） | 無料枠あり（100通/日）だがカード登録必須 | 中 | ○ | 無料枠のカード登録必須が制約 |
| LINE通知（LINE Notify） | 無料 | 易 | ○ | 2025年4月にサービス終了済み |
| Web Push（VAPID） | 完全無料（自前サーバー） | 中 | ○ | ブラウザが端末に直接プッシュ。カード登録不要 |

**選定: Web Push（VAPID自前配信）**。月額0円・カード登録不要・モバイルブラウザ（Chrome/Firefox/Edge/Safari iOS17+）対応・backend が VAPID キーペアを保持して直接プッシュするため外部有料サービス不要。Render の無料インスタンスがスリープ中でも scheduler（Cloudflare Workers）が先に backend を起こしてから通知ジョブを実行することで対応する。

### 収集ソースの選定基準

- 利用規約・robots.txt で取得が許可されている公開フィード・公式API・RSSのみ採用
- 無料で安定して取れるもの（課金・審査なし）
- スクレイピングではなく公式フィード（RSS/Atom/公式API）を優先

採用ソース:
- **YouTube Data API v3**（無料枠 10,000 ユニット/日）— 公式チャンネルの動画フィード
- **X RSS プロキシ**（nitter インスタンス等の公開 RSS エンドポイント）— X は公式 API が有料のため、公開 RSS プロキシ（robots.txt 許可範囲）を使用。プロキシが停止した場合は収集をスキップしてログに記録する
- **イベント/ライブ告知**（e-plus・TicketPea 等が提供する公式 RSS/公開フィード）— 各サービスのフィード URL をタレントごとに設定

### 容量監視の手段

Neon の無料プランは 0.5 GB。直接クエリで `pg_database_size` を取得し、backend の内部 API が返すヘルスエンドポイントに追加する。scheduler の定期ジョブで週1回チェックし、閾値（400 MB）超過時に Web Push でユーザーに通知する。

## 機能一覧

### FEAT-044: Web Push 購読の管理（backend）
- **優先度**: Must
- **説明**: ユーザーがブラウザで通知を許可したとき、Push Subscription（endpoint・鍵情報）を backend に保存する。ユーザーは複数デバイスで購読でき、ログアウトや通知拒否時に購読を削除できる。VAPID の公開鍵を frontend に返す API も提供する。
- **受け入れ基準**:
  - [ ] `push_subscriptions` テーブルが存在し、ユーザーID・endpoint・p256dh・auth・登録日時を保持する
  - [ ] `GET /api/v1/push/vapid-public-key` が VAPID 公開鍵を返す（認証不要）
  - [ ] `POST /api/v1/push/subscriptions` で購読を登録できる（認証必須）
  - [ ] 同一 endpoint の二重登録はエラーにならず、既存レコードを上書きする
  - [ ] `DELETE /api/v1/push/subscriptions` で購読を削除できる（認証必須）
  - [ ] VAPID 秘密鍵は環境変数から読み込み、コードに含まない
  - [ ] Swagger に各エンドポイントが定義されている
  - [ ] `dotnet test backend` がパスする

### FEAT-045: Web Push 通知送信ジョブ（backend）
- **優先度**: Must
- **説明**: 定期実行ジョブ（collector 収集完了後またはスケジュール）の中で、各ユーザーに新着ニュース・出演情報の件数を集計し、新着がある場合のみ Web Push を送信する。通知本文には「推し名：N件の新着」を含む。無効になった endpoint（410 Gone）は自動削除する。
- **受け入れ基準**:
  - [ ] `POST /api/v1/internal/push/notify` エンドポイントが存在し、X-Api-Key で保護されている
  - [ ] 直近の通知送信以降に収集された新着アイテムがあるユーザーにのみ通知を送信する
  - [ ] 通知本文に推し名と新着件数が含まれる
  - [ ] Push送信成功・失敗・スキップ件数がログに出力される
  - [ ] endpoint が 410 Gone を返した場合、対象 push_subscription を自動削除する
  - [ ] 一時的なネットワークエラーは最大3回リトライ（指数バックオフ）する
  - [ ] `dotnet test backend` がパスする

### FEAT-046: Web Push 購読 UI（frontend）
- **優先度**: Must
- **説明**: ダッシュボードまたは設定画面に「通知を受け取る」ボタンを追加する。ブラウザが通知許可を求め、許可後に backend へ購読を登録する。許可済みの場合はボタンを「通知を解除する」に切り替え、押下で購読を削除する。通知がサポートされていないブラウザではボタンを非表示にする。
- **受け入れ基準**:
  - [ ] Service Worker が登録されている
  - [ ] 「通知を受け取る」ボタン押下でブラウザの許可ダイアログが表示される
  - [ ] 許可後に backend の購読登録 API が呼ばれ、ボタンが「通知を解除する」に変わる
  - [ ] 「通知を解除する」押下で購読削除 API が呼ばれ、ボタンが「通知を受け取る」に戻る
  - [ ] 通知がブロックされているとき、ユーザーに「ブラウザ設定から許可してください」を表示する
  - [ ] Push通知がサポートされていないブラウザではボタンが表示されない
  - [ ] 既存の Vitest テストがパスする

### FEAT-047: 通知送信の定期起動（scheduler）
- **優先度**: Must
- **説明**: Cloudflare Workers の Cron Triggers に通知ジョブの定期起動を追加する。2時間ごとの収集 cron 完了後30分に通知ジョブを呼び出すことで、収集→通知の流れを自動化する。既存の収集 cron・削除 cron は変更しない。
- **受け入れ基準**:
  - [ ] `wrangler.toml` に通知用の Cron Trigger が追加されている（例: `47 */2 * * *`）
  - [ ] Worker が `POST /api/v1/internal/push/notify` を X-Api-Key 付きで呼び出す
  - [ ] 呼び出しが失敗した場合（5xx・ネットワーク）に最大3回リトライする
  - [ ] 成功・失敗がログに出力される
  - [ ] `npm test`（scheduler/）がパスする

### FEAT-048: YouTube 動画フィードの収集
- **優先度**: Should
- **説明**: タレントに紐づく YouTube チャンネル ID を backend で管理し、YouTube Data API v3 の公開フィードからタレントの最新動画情報を収集する。収集した動画はニュースアイテムと区別するため `source_type = "youtube"` で保存する。API の無料クォータ（10,000 ユニット/日）を超えないよう、全タレント分を1サイクルで収集する件数を制限する。チャンネル ID が未設定のタレントはスキップする。
- **受け入れ基準**:
  - [ ] `talent_sources` テーブルが存在し、talent_id・source_type（"youtube"等）・source_id（チャンネルID等）・有効フラグを保持する
  - [ ] backend の管理 API（内部）でタレントへの YouTube チャンネル ID を登録・削除できる
  - [ ] collector が YouTube Data API v3 から動画リストを取得し、`news_items` として保存する
  - [ ] ソースタイプ（"youtube"）がニュースアイテムのレスポンスに含まれる
  - [ ] 1サイクルあたりの API 呼び出し回数がタレント数に比例し、クォータを超えないことをログで確認できる
  - [ ] YouTube API キーは環境変数から読み込む
  - [ ] APIキーが未設定の場合 YouTube 収集をスキップし、他の収集は継続する
  - [ ] 重複ソースURL は保存しない
  - [ ] `pytest collector` がパスする

### FEAT-049: X（旧 Twitter）公開 RSS フィードの収集
- **優先度**: Should
- **説明**: タレントの公式 X アカウント（@handle）を backend で管理し、公開 RSS プロキシ経由でタイムラインを収集する。RSS プロキシ（nitter 系インスタンス等、robots.txt 許可済み）を使用し、プロキシが停止・エラーの場合は収集をスキップしてログに記録する。収集したツイート情報は `source_type = "x_post"` で `news_items` に保存する。
- **受け入れ基準**:
  - [ ] `talent_sources` テーブルで source_type = "x_post" のレコードとして X ハンドルを登録できる
  - [ ] collector がプロキシ RSS フィードを取得し、`news_items` に保存する
  - [ ] プロキシが HTTP エラー（4xx・5xx）を返した場合、スキップして警告ログを出力し他のタレントの収集を続行する
  - [ ] 収集したアイテムに `source_type = "x_post"` が設定されている
  - [ ] X ハンドルが未設定のタレントはスキップする
  - [ ] 重複ソースURL は保存しない
  - [ ] `pytest collector` がパスする

### FEAT-050: イベント/ライブ告知 RSS の収集
- **優先度**: Could
- **説明**: タレントに紐づくイベント・ライブ告知の RSS フィード URL を backend で管理し、collector が定期取得する。収集したアイテムは `source_type = "event"` で `news_items` に保存する。フィード URL が未設定のタレントはスキップする。利用規約で禁止されているサービスや robots.txt で取得が禁止されているフィードは対象に含めない。
- **受け入れ基準**:

  - [ ] collector がフィードを取得し、`news_items` に保存する
  - [ ] アイテムに `source_type = "event"` が設定されている
  - [ ] フィード取得エラー時はスキップして警告ログを出力する
  - [ ] 重複ソースURL は保存しない
  - [ ] `pytest collector` がパスする

### FEAT-052: 収集失敗の検知と管理者通知（backend + collector）
- **優先度**: Must
- **説明**: collector のジョブ実行結果（成功・失敗・スキップ件数・エラー内容）を backend に記録する（既存 `CollectorJobLog` の拡張）。連続して一定回数失敗したタレントや全体収集の連続失敗を検知し、ユーザー（購読している場合）または Web Push で警告通知する。収集失敗が続いていることがダッシュボードの運用パネルに表示される。
- **受け入れ基準**:
  - [ ] `collector_job_logs` テーブルに失敗理由・エラーメッセージ・対象タレントID を保存できる
  - [ ] 同一タレントが3サイクル連続で収集失敗している場合、次回の通知ジョブ実行時に警告 Push を送信する
  - [ ] 全体収集が3サイクル連続失敗している場合も警告 Push を送信する
  - [ ] 警告 Push の本文に「○○の収集が連続して失敗しています」等の内容が含まれる
  - [ ] ダッシュボードの運用パネルに直近24時間の収集ジョブの成功/失敗状況が表示される
  - [ ] 警告 Push 送信後、次のサイクルで収集が成功した場合は警告を解除する（重複送信しない）
  - [ ] `dotnet test backend` がパスする

- **受け入れ基準**:

  - [ ] ダッシュボードの運用パネルに現在の DB 使用量と使用率（%）が表示される

## UXフロー

### 通知のフロー

1. ユーザーがダッシュボードを開くと「通知を受け取る」ボタンが表示される
2. ボタンを押すとブラウザの通知許可ダイアログが表示される
3. 許可すると Push Subscription が backend に登録され、ボタンが「通知を解除する」に変わる
4. 以降、2時間ごとの収集後30分に新着がある場合のみ Push 通知が届く
5. 通知をタップするとダッシュボードが開き、新着アイテムが確認できる
6. 「通知を解除する」で購読を削除でき、以降は通知が届かない

### 収集ソース拡充のフロー

1. ユーザーが推し詳細または設定画面を開く
2. YouTube チャンネル・X ハンドル・イベント RSS URL を入力してソースを登録する
3. 次の収集サイクルから登録したソースも対象になる
4. 収集されたアイテムがソースタイプのバッジ付きでフィードに表示される
5. ソースタイプのフィルタで特定のソースのみを絞り込める

### 運用監視のフロー

1. scheduler が週1回 DB 容量をチェックし、400 MB を超えると Push 通知が届く
2. ダッシュボードの運用パネルで現在の DB 使用量が確認できる
3. 収集が連続して失敗した場合も Push 通知が届く
4. 運用パネルで失敗中のタレントと連続失敗回数を確認できる

## 非機能要件

- **信頼性**: Push 送信失敗（410 Gone を除く）は3回リトライする。収集失敗が3サイクル続くと通知で検知できる。scheduler の各 cron が独立しており、1つが失敗しても他は継続する
- **セキュリティ**: VAPID 秘密鍵・YouTube API キー・X RSSプロキシURL はすべて環境変数で管理し、コードやログに露出しない。Push 送信エンドポイントは X-Api-Key で保護する
- **パフォーマンス**: YouTube Data API v3 のクォータ（10,000 ユニット/日）を超えないよう、1サイクルあたりの呼び出し数をタレント数に応じて制限し、ログに残す。DB 使用量クエリは週1回のみとし、通常の API レスポンスタイムに影響を与えない
- **コスト**: 追加の有料サービスを使わない。Web Push は VAPID 自前配信で無料。YouTube API は無料枠（10,000 ユニット/日）内に収める。X 収集は公開 RSS プロキシ経由で追加費用なし
- **拡張性**: `talent_sources` テーブルで新しいソースタイプを追加しやすい設計にする。source_type の判定ロジックはコードの1か所にまとめる
