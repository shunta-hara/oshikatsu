# 推し活トラッキング 仕様書

## 概要

「oshikatsu」は、アイドル・アーティスト・キャラクターなど「推し」を持つファンが、推しに関する最新情報を見逃さないために使うウェブサービスである。ユーザーが推しの名前を登録するだけで、出演番組やニュースが自動収集され、ひとつの画面から確認できる。情報の取りこぼしを減らし、推し活の情報収集コストを下げることが目的である。対象ユーザーは複数の推しを追う国内ファン全般。

---

## 機能一覧

### FEAT-001: ユーザー登録・ログイン
- **優先度**: Must
- **説明**: メールアドレスとパスワードによる新規登録・ログイン・ログアウトを提供する。認証済みユーザーのみが推し情報を登録・閲覧できる。セッションはトークンベースで管理し、有効期限を設ける。
- **受け入れ基準**:
  - [ ] 未登録のメールアドレスで新規登録できる
  - [ ] 登録済みのメールアドレスで再登録しようとするとエラーになる
  - [ ] 正しいメールアドレス・パスワードでログインできる
  - [ ] 誤ったパスワードでログインしようとするとエラーになる
  - [ ] ログアウト後は認証が必要なページへアクセスできない

### FEAT-002: 推し登録・管理
- **優先度**: Must
- **説明**: ユーザーが推しの名前を登録・編集・削除できる。推しはユーザーごとに管理され、他のユーザーからは見えない。1ユーザーが登録できる推しの上限は初期実装では20件とする。
- **受け入れ基準**:
  - [ ] 推しの名前を入力して登録できる
  - [ ] 登録済みの推しを一覧で確認できる
  - [ ] 登録済みの推しを削除できる
  - [ ] 20件を超えて登録しようとするとエラーになる
  - [ ] 他のユーザーが登録した推しは自分の一覧に表示されない

### FEAT-003: バックエンドAPI基盤・OpenAPI定義
- **優先度**: Must
- **説明**: すべての API エンドポイントを REST で公開し、OpenAPI（Swagger）仕様として自動生成・公開する。frontend と collector はこの定義を契約として参照する。エンドポイントはバージョンプレフィックス（`/api/v1/`）を付与する。
- **受け入れ基準**:
  - [ ] `/swagger` にアクセスすると Swagger UI が表示される
  - [ ] 全エンドポイントが OpenAPI 定義に含まれている
  - [ ] 認証が必要なエンドポイントは定義上でも認証必須と明示されている

### FEAT-004: DBスキーマ確立（User / Oshi / NewsItem / ProgramAppearance）
- **優先度**: Must
- **説明**: PostgreSQL 上に4つのコアエンティティを定義する。スキーマ変更はすべてマイグレーションで管理する。backend が正本であり、collector・frontend はこのモデルに従う。
- **受け入れ基準**:
  - [ ] `users` テーブルが存在し、メールアドレスとハッシュ化パスワードを保持する
  - [ ] `oshis` テーブルが存在し、ユーザーIDと推しの名前を保持する
  - [ ] `news_items` テーブルが存在し、推しID・タイトル・本文要約・ソースURL・公開日時・収集日時を保持する
  - [ ] `program_appearances` テーブルが存在し、推しID・番組名・放送局・放送日時・ソースURL・収集日時を保持する
  - [ ] マイグレーションファイルが `backend/` に存在し、`dotnet ef database update` で適用できる

### FEAT-005: collector書き込み方式の確立
- **優先度**: Must
- **説明**: collector が収集したデータをどう永続化するかの方式を決定し、`docs/` に記録する。初期実装では backend が提供する内部 API 経由の書き込みを採用し、collector が直接 DB に触れない構成にする。内部 API には collector 専用の API キー認証を設ける。
- **受け入れ基準**:
  - [ ] `docs/collector-write-strategy.md` に方式・理由・API エンドポイント仕様が記録されている
  - [ ] collector から内部 API を叩くとデータが DB に保存される
  - [ ] 正しい API キーなしにアクセスすると 401 が返る
  - [ ] API キーはコードにハードコードされておらず、環境変数から読み込まれる

### FEAT-006: ニュース収集バッチ
- **優先度**: Must
- **説明**: collector が定期的に（初期実装では1時間ごと）各推しの名前でニュースを検索し、新着記事を backend 内部 API 経由で保存する。収集元は Google News RSS など robots.txt が許可する公開フィードを使用する。重複記事（同一ソースURL）は保存しない。
- **受け入れ基準**:
  - [ ] 登録済みの推し全員分のニュースを1サイクルで収集できる
  - [ ] 同一ソースURLのニュースは重複保存されない
  - [ ] 収集成功・失敗・件数がログに出力される
  - [ ] ネットワークエラー時はリトライ（指数バックオフ、最大3回）してから失敗ログを出力する
  - [ ] タイムアウトが設定されており、1リクエストが無限に待たない

### FEAT-007: 出演番組収集バッチ
- **優先度**: Must
- **説明**: collector が定期的に各推しの名前で出演番組情報を収集し、backend 内部 API 経由で保存する。収集元は公開されているTV番組表APIや番組ガイドサイトの許可されたフィードを使用する。FEAT-006 と同様のリトライ・重複排除ルールを適用する。
- **受け入れ基準**:
  - [ ] 登録済みの推し全員分の出演番組を1サイクルで収集できる
  - [ ] 同一ソースURLの番組情報は重複保存されない
  - [ ] 収集成功・失敗・件数がログに出力される
  - [ ] ネットワークエラー時はリトライ（指数バックオフ、最大3回）してから失敗ログを出力する

### FEAT-008: ニュース・出演番組一覧表示
- **優先度**: Must
- **説明**: ログイン済みユーザーが、自分の推し全員に関するニュースと出演番組を新着順で一覧できる。各アイテムにはタイトル・日時・ソースURL（外部リンク）を表示する。表示件数はページネーション（1ページ20件）で制御する。
- **受け入れ基準**:
  - [ ] ログイン後のトップ画面でニュースと出演番組の一覧が表示される
  - [ ] 一覧は収集日時の新しい順に並ぶ
  - [ ] 各アイテムのソースURLをクリックすると外部サイトが新しいタブで開く
  - [ ] 1ページ20件のページネーションが機能する
  - [ ] 収集データが0件の場合は「まだ情報がありません」などの空状態メッセージが表示される

### FEAT-009: 収集アイテムのソースURL・日時保持
- **優先度**: Must
- **説明**: collector が収集したすべてのアイテムに、収集元のURL・公開日時・collector が収集した日時の3点を必ず付与する。公開日時が取得できない場合は収集日時で代替するが、その旨を区別できるフラグを持つ。
- **受け入れ基準**:
  - [ ] すべてのニュース・番組アイテムにソースURLが存在する
  - [ ] すべてのアイテムに収集日時（UTC）が存在する
  - [ ] 公開日時が取得できた場合と推定の場合を区別できる

### FEAT-010: 推し別フィルタリング

- **受け入れ基準**:

### FEAT-011: 収集ジョブのログ・健全性確認

- **説明**: 特定のニュース記事をブックマーク（お気に入り）に登録し、ブックマーク一覧として確認できるようにする。後で読み返したい記事を手軽に保存する用途を想定する。

### FEAT-017: UTC以外のオフセット付き日時での500エラー修正
- **優先度**: Must
- **説明**: Npgsql は PostgreSQL の timestamptz カラムに UTC（オフセット0）以外の DateTimeOffset を書き込めず、`+09:00` などのオフセット付き日時を受け取ると500エラーになる。番組情報登録・ニュース登録・ジョブログの executedAt など、日時フィールドを受け取るすべてのエンドポイントで、受信した DateTimeOffset を UTC に変換してから DB に渡すよう修正する。
- **受け入れ基準**:
  - [ ] `POST /api/v1/internal/programs` に `airedAt: "2026-10-05T20:00:00+09:00"` を送っても 500 にならない
  - [ ] `GET /api/v1/news?from=2026-10-02T00:00:00+09:00` が 500 にならない
  - [ ] `GET /api/v1/programs?to=2026-10-05T23:59:59+09:00` が 500 にならない
  - [ ] UTC で送った場合と JST で送った場合で同じ時刻として扱われる
  - [ ] 日時フィールドを持つすべての内部 API・公開 API が修正対象になっている

### FEAT-018: 日付範囲フィルタのJST基準化
- **優先度**: Must
- **説明**: 日付範囲フィルタがユーザーの入力した日付を UTC 0:00〜23:59:59.999 に変換しているため、日本のユーザーには選択日がJSTで9時間ずれる（「10/2」を選ぶと JST 10/2 9:00〜10/3 8:59 が対象になる）。ユーザーが選んだ日付を日本時間（JST、UTC+09:00）の 0:00〜23:59:59.999 として API に渡すよう frontend を修正する。ニュース・出演番組の両方が対象。
- **受け入れ基準**:
  - [ ] 「2026-10-02」を開始日に選ぶと、API には `from=2026-10-02T00:00:00+09:00` 相当の値が送られる
  - [ ] 「2026-10-02」を終了日に選ぶと、API には `to=2026-10-02T23:59:59.999+09:00` 相当の値が送られる
  - [ ] ニュース一覧・出演番組一覧の両方で同様に動作する
  - [ ] FEAT-017 修正済みの backend が +09:00 オフセットを正しく処理する

### FEAT-019: 共通スタイル・ナビゲーション統一
- **優先度**: Must
- **説明**: 全画面でCSSが一切適用されておらず素のHTMLの状態である。また、ダッシュボードとブックマーク一覧の間の移動手段がなく、ブックマーク一覧のみフォントが異なるなど統一感がない。全画面に共通ナビゲーションバー（ダッシュボード・ブックマーク一覧・ログアウト）とシンプルで統一されたスタイルを適用し、スマートフォン幅でも崩れないレイアウトにする。
- **受け入れ基準**:
  - [ ] 全画面（ログイン・新規登録・ダッシュボード・推し管理・ブックマーク一覧）で同じフォント・配色・余白が適用されている
  - [ ] 認証済み画面にナビゲーションバーが表示され、ダッシュボード・ブックマーク一覧・ログアウトへのリンクが含まれる
  - [ ] ダッシュボードからブックマーク一覧へ、ブックマーク一覧からダッシュボードへナビゲーションから移動できる
  - [ ] スマートフォン幅（375px以上）で横スクロールが発生しない
  - [ ] ブックマーク一覧と他の画面でフォントが統一されている

### FEAT-020: frontendのAPIベースURL環境変数化・SPAルーティング
- **優先度**: Must
- **説明**: 本番環境では frontend (Cloudflare Pages) と backend (Render) のオリジンが異なるため、ビルド時の環境変数で backend の URL を指定できるようにする。また Cloudflare Pages での SPA ルーティングには全パスを `index.html` にフォールバックする設定ファイルが必要。開発時は従来どおり Vite プロキシが使用される。
- **受け入れ基準**:
  - [ ] ビルド時の環境変数（`VITE_API_BASE_URL` 相当）を設定することで任意の backend URL に API リクエストを向けられる
  - [ ] 環境変数未設定の場合は開発用の Vite プロキシ設定で動作する（既存の開発フローが壊れない）
  - [ ] `frontend/public/_redirects` が存在し、全パスを `index.html` にフォールバックする設定になっている
  - [ ] `npm run build` がエラーなく完了し、ビルド成果物に `_redirects` が含まれる

### FEAT-021: backendのコンテナ化・CORS環境変数化・HTTPS設定・マイグレーション本番適用
- **優先度**: Must
- **説明**: backend を Docker コンテナとして Render 上で動かすための準備をする。DB接続文字列・JWT秘密鍵・collector APIキー・CORS許可オリジンはすべて環境変数から読む。Render のリバースプロキシ（X-Forwarded-* ヘッダー）との整合性を確保する。コンテナ起動時にマイグレーションが自動適用される仕組みを用意する。
- **受け入れ基準**:
  - [ ] `backend/Dockerfile` が存在し、`docker build` でローカルビルドが完了する
  - [ ] ローカルで環境変数を渡して `docker run` するとコンテナが起動し、`GET /api/v1/health` が 200 を返す
  - [ ] CORS 許可オリジンを環境変数で設定でき、Cloudflare Pages のオリジンを追加できる
  - [ ] コンテナ起動時にマイグレーションが自動で適用され、手動での DB 変更が不要になる
  - [ ] リバースプロキシ環境での HTTPS 終端後に `UseHttpsRedirection` が無限リダイレクトを引き起こさない
  - [ ] 秘匿情報（接続文字列・JWT秘密鍵・APIキー）がコードおよび Dockerfile にハードコードされていない

### FEAT-022: collectorのGitHub Actions定期実行・コールドスタート対策
- **優先度**: Must
- **説明**: collector を GitHub Actions の schedule イベントで6時間ごとに定期実行する。backend の URL と API キーは GitHub Secrets から渡す。Render のコールドスタート（スリープ復帰に約1分）を考慮し、collector は収集開始前に backend のヘルスエンドポイントを確認して起動を待ってから収集を開始する。手動実行（workflow_dispatch）にも対応する。
- **受け入れ基準**:
  - [ ] `.github/workflows/collect.yml` が存在し、6時間ごとの schedule と workflow_dispatch で collector が実行される
  - [ ] backend URL と API キーは workflow ファイルにハードコードされておらず、GitHub Secrets から参照される
  - [ ] collector は収集開始前に `GET /api/v1/health` を最大2分間リトライして backend の起動を確認する
  - [ ] ヘルスチェックがタイムアウトした場合は収集をスキップしてエラーログを出力する
  - [ ] ローカルで `pytest collector` が正常にパスする

## UXフロー

### 初回利用フロー
1. ユーザーがサービスにアクセスし、新規登録画面からメールアドレス・パスワードを入力して登録する
2. ログイン後、推し登録画面が表示される（または登録を促すメッセージが表示される）
3. 「推しを追加」から推しの名前（例：「鈴木一郎」）を入力して登録する
4. 登録完了後、ダッシュボード（一覧）に遷移するが、まだ収集が走っていないため空状態メッセージが表示される
5. 次の収集サイクル（最長1時間後）に自動でニュース・番組情報が収集される
6. 再訪時、一覧に最新のニュース・出演番組が並んでいる

### 日常利用フロー
1. ユーザーがサービスにログインする
2. トップ一覧で推し全員の最新ニュース・出演番組を新着順に確認する
3. 気になる記事のタイトルをクリックしてソースサイトを閲覧する
4. 特定の推しだけの情報を見たい場合、推し選択UIで絞り込む

### 推し管理フロー
1. 推し一覧画面で「追加」から新しい推しを登録する
2. 不要になった推しは「削除」ボタンで削除する（以降の収集対象から外れる）
3. 既存の収集済みデータは削除後も残るか消えるかは初期実装では「残す」方針とする（仕様拡張余地）

### ナビゲーションフロー（FEAT-019）
1. ログイン後のすべての画面上部にナビゲーションバーが表示される
2. 「ダッシュボード」リンクで推し全員の一覧ページへ移動できる
3. 「ブックマーク」リンクでブックマーク一覧ページへ移動できる
4. 「ログアウト」リンクでログアウトしてログイン画面へ戻る
5. ブックマーク一覧から「ダッシュボード」リンクで一覧に戻れる（専用の「戻る」ボタン不要）

## 非機能要件

- **信頼性**: collector バッチは定期実行（初期6時間間隔）し、一時的なネットワーク障害では最大3回リトライする。バッチ失敗は必ずログに残す
- **セキュリティ**: パスワードはハッシュ化保存。APIキー・DB接続文字列・外部サービス認証情報はコードにハードコードせず環境変数で管理する。collector の内部APIはAPIキー認証で保護する
- **パフォーマンス**: 一覧APIは1ページ20件のページネーションを必須とし、全件取得APIは提供しない。1ユーザーあたり推し20件・アイテム合計数千件規模での応答を想定する
- **トレーサビリティ**: 収集したすべてのアイテムにソースURL・公開日時・収集日時を保持し、情報源を後から追跡できる
- **拡張性**: collector の収集ソース追加は既存のバッチ構成を変更せずに新モジュールを追加することで対応できる構成にする
- **日時の正規化**: backend はオフセット付きの DateTimeOffset をすべて UTC に変換してから DB に書き込む。frontend は日付入力を JST (UTC+09:00) の日境界として API に渡す
- **デプロイ可用性**: 接続文字列・JWT秘密鍵・APIキー・CORS設定はすべて環境変数から読み、環境変数だけを差し替えることで開発・本番を切り替えられる。Docker イメージはローカルでビルド・起動を検証できる
- **コールドスタート対応**: Render のスリープ復帰（約1分）に備え、collector は収集前にヘルスチェックで backend の起動を確認してから収集を開始する
